Desktop control for AI agents · Linux · Wayland

Your agent can run commands. Now it can use the screen.

NexRemote turns a Linux desktop into shell commands: every window, a real mouse and keyboard, buttons pressed by name, and the terminals you already have open, other agents included. No root, no SDK, and a vision model only when an app gives it nothing else to read.

01

The problem

Agents live in the terminal. Your work lives on the screen.

Coding agents edit files and run builds. The moment a task needs a settings dialog, a running app or another terminal, they stop and hand it back to you. The usual ways around that each break somewhere.

  1. A

    Screenshot every step

    The model looks at the whole screen, guesses coordinates, clicks, then takes another screenshot to see what happened.

    Where it breaks: every step is a vision call, so it is slow and costly, and a few pixels off is a wrong click. Text already on screen is read back from an image.

  2. B

    An integration per app

    APIs, SDKs and browser drivers are exact, but each one covers a single program and has to be built and maintained.

    Where it breaks: desktop apps without an API, and the terminals already open on screen, stay out of reach.

  3. C

    X11 automation scripts

    xdotool and similar tools were made for X11, where any client could read and type into any window.

    Where it breaks: Wayland closed that door. The usual workaround, ydotool, writes to /dev/uinput, which needs root or a udev rule.

NexRemote takes the most direct channel the desktop already offers, and falls back to pixels only when nothing else is there.

02

How it works

Structure first. Pixels last.

Before it looks at a single pixel, NexRemote asks the desktop what it already knows. Each step down is used only when the one above has nothing to give.

  1. 1

    Ask the window manager

    KWin lists every window with its title, app, position and focus. The agent can bring one forward, minimize or close it, including apps that publish nothing else.

    Channel KWin scripting Model receives text

    $ nexremote windows
* win:{c31f…}  org.kde.konsole  1100x780+0+0      nexwatch : claude-bin — Konsole
  win:{8c1e…}  systemsettings   760x540+1180+60   Appearance — System Settings
  win:{a41f…}  zen              880x560+1060+520  Player — Zen Browser
  2. 2

    Read the accessibility tree, act by name

    Buttons, switches and fields come with names and roles. The agent presses “Dark” by its name. The mouse does not move, and nothing depends on where the control is drawn.

    Channel AT-SPI Model receives text

    $ nexremote find "Dark" --window win:{8c1e…}
atspi:4:0/2/7	[checkbox] Dark  <toggle,click>
$ nexremote click atspi:4:0/2/7 --json
{ "ok": true, "ref": "atspi:4:0/2/7" }
  3. 3

    Read terminal text directly

    Konsole tabs and tmux panes hand over their text, along with the program running in each. No screenshot, no OCR, no focus change.

    Channel Konsole D-Bus · tmux Model receives text

    $ nexremote term-read konsole:7891:2
● Running test suite…
  tests/test_api.py ........F.F
✗ 2 failed · test_login, test_refresh
Should I fix them? (y/n, or tell me)
  4. 4

    Only then: screenshot and click pixels

    For browsers, games and most Electron apps. The shot is cropped to one window and scaled for the model; a pixel in that image is mapped back to the screen and clicked through the RemoteDesktop portal.

    Channel spectacle / grim · RemoteDesktop portal Model receives one image

    $ nexremote screenshot --window win:{a41f…} --max-width 1568
$ nexremote click 440 190 --from-shot --json
{ "ok": true, "x": 1500, "y": 710, "button": "left" }

$ nexremote windows

Model receives text

structured pixels

One core between any agent and the desktop

Adapters only know the core; the core only talks to channels the desktop already provides. If a backend is missing, the rest keep working and nexremote caps says what is off.

05

Terminals

Eight agents open? One of them can run the others.

Every Konsole tab and tmux pane is listed with the program in its foreground. An agent can read another agent's screen, answer its question, or stop it with --key C-c.

None of it needs window focus or your keyboard. You keep working while it does.

06

Last resort

When an app has nothing to read, it looks.

Browsers, games and most Electron apps publish no controls. Take a screenshot cropped to one window and scaled for the model; it clicks on pixels in that image and NexRemote converts them back to the screen.

screen = origin + image ÷ scale
(3000, 0) + (412, 230) ÷ 0.8333 = (3494, 276)

09

Why now

The pieces are in place.

No forecast needed. This is where the tools already are.

  1. Agents already work in terminals

    Coding agents such as Claude Code, Codex, Aider and Gemini CLI run in a shell. A shell command is the one interface they all share, so that is the interface NexRemote speaks.

  2. MCP became a common tool protocol

    Editors and agent clients load tools over MCP. One NexRemote server gives all of them the same desktop tools, with screenshots returned as images.

  3. Linux desktops moved to Wayland

    Wayland removed the X11 shortcuts that old automation relied on. The sanctioned way in is the xdg-desktop-portal RemoteDesktop interface, which asks the user once. NexRemote is built on it.

Roadmap

What exists, what comes next

The left column ships in the download today. The right column is planned, not built.

In v0.2.0 today

  • Every window through KWin scripting
  • Mouse and keyboard through the RemoteDesktop portal, approved once
  • Reading and typing into open Konsole tabs and tmux panes
  • 21 MCP tools, 26 CLI commands, an HTTP API and a text loop for models without tool calling
  • Input tests that run in an isolated sandbox desktop

Planned

  • Electron accessibility wrapper. Start Electron apps with --force-renderer-accessibility automatically, so their buttons can be pressed by name instead of by pixel.
  • GNOME and wlroots validation. Test the portal path on GNOME and on wlroots compositors such as Sway, and document what works.
  • Remote deployment. Ship the HTTP adapter with a systemd unit for running on another machine.
  • Live window tree over MCP. Serve the window list and accessibility tree as MCP resources, alongside the tools.
11

Connect

Plug it into your agent

Same core, four ways in. Pick whatever your harness already speaks.

Any harness that can run a command: Claude Code, Codex, Aider, opencode, a cron job. Give the agent the skill text and it knows the rest.

nexremote skill        # paste into your agent's instructions
nexremote observe --json

21 tools over stdio for Claude Code, Claude Desktop, Cursor and other MCP clients. Screenshots come back as images the model can look at.

claude mcp add nexremote -- ~/bin/nexremote-mcp

For agents on another machine. Listens on localhost by default and refuses any other address without a token.

nexremote-http --port 8788 --token "$SECRET"
curl -s -H "Authorization: Bearer $SECRET" -X POST localhost:8788/terminals

For local models without tool calling. The model writes nexremote lines; the loop runs them and feeds the output back until it writes DONE.

nexremote-agent --model-cmd "ollama run qwen2.5" \
  --goal "Open the calculator, compute 7×8, read the result"
12

Safety

What it does to your machine

Asks once
KDE shows a remote-control dialog the first time. Tick Allow restoring and it won't ask again. Delete ~/.config/nexremote/portal.json to take it back.
Gives your pointer back
Wayland has one pointer. A click borrows it and returns it to where it was.
No root
No /dev/uinput, no daemon running as another user.
Closed to the network
The HTTP adapter will not listen beyond localhost without a token.
Tested where it can't hurt you
Input tests run in a throwaway desktop with its own D-Bus, a virtual KWin, its own portal and PipeWire.

Limits

  • Tested on KDE Plasma 6 (Wayland). GNOME should work through the same portal, but the window list falls back to accessibility. wlroots compositors are untested.
  • Konsole exposes the visible screen only. For scrollback, run the agent in tmux.
  • Browsers and Electron apps are driven by screenshot and coordinates.

Install

Install in three steps

  1. Download and unpack

    unzip nexremote.zip && cd nexremote

    nexremote.zip (82 KB) · nexremote.tar.gz (63 KB)

  2. Install the commands

    ./install.sh

    Puts nexremote, nexremote-mcp, nexremote-http and nexremote-agent in ~/bin, then lists anything missing.

  3. Grant access once

    nexremote setup && nexremote caps

    Turns on the accessibility tree and opens KDE's remote-control dialog: tick Allow restoring, press Share.

Needs python3-dbus python3-gi xdg-desktop-portal-kde pipewire wl-clipboard. Optional: tmux python3-pil python3-xlib, pip install mcp.
