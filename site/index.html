AI agents · desktop + terminal

Give your agent hands.

NexRemote lets an AI agent see a real desktop and drive a real terminal — buttons by name, not by pixel. It plugs into any harness and any model: if the thing can run one shell command, it can use NexRemote.

The whole interface is a shell command.

      

        No SDK to import, no tool-calling schema to implement, no MCP client
        required. NexRemote is a CLI first. Everything else is a wrapper over it.
      

    

    

      

        
nexremote observe
# → windows, accessible tree, terminal sessions
nexremote find "Save"
# → atspi:9:0/0/12  [button] Save  <click>
nexremote click atspi:9:0/0/12
# → clicked

        
      

    

  


  
  

    
Two backends, one contract

    

      The core knows how to act. Adapters know how to be called. Neither one
      knows the other exists.
    


    

      

        01
        
See — GUI

        

          Reads the accessibility tree every GTK/Qt app already publishes. Each
          button, menu and field arrives as a name, a role and the actions it
          accepts. Click by name; pixels never enter the picture.
        

        gui.py · AT-SPI
      

      

        02
        
See — terminal

        

          Drives a tmux session and reads its screen back as text. Start a
          script, a REPL, or a whole TUI and watch what it prints — in a later,
          separate call. Sessions persist between invocations.
        

        tui.py · tmux / PTY
      

      

        03
        
Speak — adapters

        

          MCP server, CLI, HTTP API, and a plain-text protocol for models
          without tool-calling. Point whichever one your harness understands.
        

        adapters/ · mcp · http · cli
      

    

  


  
  

    
How a request travels

    
From an agent's intent to a real click — and back.

    

      
      
    

  


  
  

    
Pick the way you call it

    
Same five verbs everywhere. Only the transport changes.


    

      
      
      
      
    


    

      

        
Any harness that can run a shell command — including a proxied or
           custom CLI. Nothing to register.

        
nexremote run "ls -la" --json
nexremote screen --session build
nexremote keys "C-c" --session build

      

      

        
Thirteen tools over stdio. Drop this into the client's MCP config.

        
{
  "mcpServers": {
    "nexremote": { "command": "nexremote-mcp" }
  }
}

      

      

        
Standard library only. Bind it to a token before you expose it.

        
nexremote-http --port 8788 --token $SECRET

curl -s -X POST localhost:8788/run \
  -d '{"command":"uptime"}'

      

      

        
No tool-calling? The model writes nexremote … lines; the
           loop runs them and feeds the output back. Works with any text model.

        
nexremote-agent \
  --model-cmd "ollama run qwen2.5" \
  --goal "open the calculator, compute 7×8"

What it wants

        
    
          
  • ✓ tmux terminal backend
    • 
          
  • ✓ wtype Wayland input
    • 
          
  • ✓ python3-gi AT-SPI
    • 
          
  • ○ mcp only for the MCP adapter
    • 
        

        
Missing pieces degrade gracefully — the terminal side
           still works with no GUI at all.

      

    

  


  
  

    
What it won't do

    

      

        
Electron apps hide their buttons

        
Discord, VS Code and friends don't publish their inner widgets unless
           launched with --force-renderer-accessibility.

      

      

        
Screenshots are pixels, not understanding

        
screenshot returns a PNG. Reading it is the job of a
           vision model — NexRemote itself reasons over structure.

      

      

        
No GUI, no clicks

        
On a headless box the GUI backend reports itself unavailable. Terminal
           verbs keep working.
